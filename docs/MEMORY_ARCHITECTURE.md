## 1. Концепция и назначение

Memory Engine решает фундаментальную проблему персональных ассистентов — потерю контекста ("синдром золотой рыбки") без засорения контекстного окна избыточным шумом диалога.

В отличие от систем, механически сохраняющих все сообщения чата или полагающихся на бесконечный контекст, Personal AI Brain разделяет кратковременный буфер диалога и структурированную долговременную память.

### Ключевые архитектурные принципы:
1. **Строгая политика допуска (Admission Policy):** предварительная фильтрация сообщений до их записи.
2. **Взвешенный ретривал (Scored Retrieval):** трехфакторный скоринг (релевантность, важность, свежесть).
3. **Разрешение смысловых конфликтов (Conflict Resolution):** автоматическая инвалидация (`SUPERSEDED`) устаревших или отмененных фактов.
4. **Изоляция пространств:** возможность привязки воспоминаний к конкретным клиентам (`client_id`) и проектам (`project_id`).
5. **Право на забвение (Right to be Forgotten):** атомарное удаление и полный сброс памяти пользователя.

## 3. Политика допуска (Admission Policy)

Метод `evaluate_admission(text: str) -> AdmissionDecision` анализирует входящий текст и принимает одно из четырех решений (`AdmissionAction`):

```
                       Входящий текст сообщения
                                   |
                                   v
             Длина < 8 симв. ИЛИ разговорный филлер?  --- ДА ---> [ACTION: IGNORE]
             ("привет", "ок", "спасибо", "ясно", "да")            (Не сохраняется)
                                   |
                                  НЕТ
                                   v
             Указание правила / табу / стиля общения? --- ДА ---> [ACTION: SAVE]
             ("не используй", "предпочитаю", "стиль")              (Type: PREFERENCE, Imp: 0.95)
                                   |
                                  НЕТ
                                   v
             Транзакция / договоренность по клиенту?  --- ДА ---> [ACTION: SAVE]
             ("клиент выбрал", "пакет", "оплатил")                 (Type: CLIENT/PROJECT, Imp: 0.85)
                                   |
                                  НЕТ
                                   v
             Идентичность автора / специализация?    --- ДА ---> [ACTION: SAVE]
             ("я работаю", "я фотограф", "мой город")              (Type: PROFILE, Imp: 0.90)
                                   |
                                  НЕТ
                                   v
             Временное намерение ("сегодня хочу")?   --- ДА ---> [ACTION: TEMPORARY]
             ("надо сегодня", "планирую сегодня")                  (Type: TEMPORARY, TTL: 24h)
                                   |
                                  НЕТ
                                   v
             Общий объективный факт о мире/бизнесе   ----------> [ACTION: SAVE]
                                                                   (Type: FACT, Imp: 0.50)
```

## 4. Алгоритм взвешенного ретривала (Scored Retrieval)

При формировании контекста память ранжируется по комбинированной математической формуле:

$$\text{Score} = w_{\text{rel}} \cdot \text{Relevance} + w_{\text{imp}} \cdot \text{Importance} + w_{\text{rec}} \cdot \text{Recency}$$

где:
- $w_{\text{rel}} = 0.50$ — вес семантической релевантности запросу пользователя;
- $w_{\text{imp}} = 0.30$ — вес абсолютной важности факта;
- $w_{\text{rec}} = 0.20$ — вес свежести записи.

### Механика расчета метрик:
1. **Relevance ($\text{Relevance}$):**
   - Нормализованное лексическое пересечение множеств токенов запроса и содержания воспоминания:
     $$\text{Relevance} = \frac{|\text{Tokens}_{\text{query}} \cap \text{Tokens}_{\text{mem}}|}{\min(|\text{Tokens}_{\text{query}}|, 10)}$$
   - При наличии явных ключевых слов стиля (`стиль`, `правило`, `ответ`, `как`) фактам с типами `PREFERENCE` и `STYLE` назначается защитный порог $\text{Relevance} \ge 0.40$.
   - **Порог отсечения (`min_relevance = 0.15`):** факты с релевантностью ниже 0.15 (не имеющие отношения к запросу) жестко отсекаются и не передаются в модель. Факт о домашнем питомце никогда не попадет в промпт с вопросом о настройке света.
2. **Importance ($\text{Importance}$):**
   - Значение от 0.1 до 1.0, определенное при сохранении или обновлении.
3. **Recency ($\text{Recency}$):**
   - Экспоненциальное линейное затухание с периодом полураспада 30 дней:
     $$\text{Recency} = \max\left(0.0, 1.0 - \frac{\text{Age in Days}}{30.0}\right)$$

## 5. Разрешение конфликтов (Conflict Resolution & Superseding)

Человек регулярно меняет привычки, настройки и цены. Если ассистент хранит противоречащие факты, модель неизбежно галлюцинирует или путается.

### Логика работы:
1. Перед фиксацией новой записи метод `_resolve_conflicts(new_content, m_type, new_mem_id)` ищет активные записи того же типа.
2. При обнаружении семантического противоречия (например, старое правило *"краткие ответы в 1 предложение"* против нового *"теперь подробные академические ответы с разбором"*):
   - Старая запись обновляется: `status = 'SUPERSEDED'`, `superseded_by = <new_mem_id>`.
   - Записывается время инвалидации `updated_at`.
3. В поисковой выборке (`retrieve_relevant_memories`) участвуют **только** записи со статусом `ACTIVE`.

## 6. Схема таблицы базы данных (`memories`)

```sql
CREATE TABLE IF NOT EXISTS memories (
    id TEXT PRIMARY KEY,
    type TEXT NOT NULL,
    content TEXT NOT NULL,
    importance REAL NOT NULL DEFAULT 0.5,
    confidence REAL NOT NULL DEFAULT 0.8,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    source TEXT NOT NULL DEFAULT 'conversation',
    project_id TEXT,
    client_id TEXT,
    expires_at TEXT,
    status TEXT NOT NULL DEFAULT 'ACTIVE',
    superseded_by TEXT,
    tags_json TEXT,
    FOREIGN KEY(project_id) REFERENCES projects(id),
    FOREIGN KEY(client_id) REFERENCES clients(id)
);

CREATE INDEX IF NOT EXISTS idx_memories_type ON memories(type);
CREATE INDEX IF NOT EXISTS idx_memories_status ON memories(status);
CREATE INDEX IF NOT EXISTS idx_memories_client ON memories(client_id);
CREATE INDEX IF NOT EXISTS idx_memories_project ON memories(project_id);
```
